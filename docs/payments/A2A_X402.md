## 対象とする仕様

この文書でいう「A2A x402」は、A2A TaskとMessage上で決済情報を交換する **A2A x402 Payments Extension v0.1** を指す。一般的なHTTP x402やx402 v2の説明ではない。

規範基準は[`secure_mediation_agent/spec_manifest.json`](../../secure_mediation_agent/spec_manifest.json)に固定している。

- repository: `google-agentic-commerce/a2a-x402`
- commit: `125db5526a965d2325459d1a9df2e274a7e42396`
- specification: `spec/v0.1/spec.md`
- specification SHA-256: `5cdc35ed8c4d7a93bb120f1782fd06e2cc3ef19036684f772e27d0d644c66940`
- canonical extension URI: `https://github.com/google-a2a/a2a-x402/v0.1`

参照先:

- [A2A x402 Payments Extension v0.1 specification](https://github.com/google-agentic-commerce/a2a-x402/blob/125db5526a965d2325459d1a9df2e274a7e42396/spec/v0.1/spec.md)
- [公式Python reference package](https://github.com/google-agentic-commerce/a2a-x402/tree/125db5526a965d2325459d1a9df2e274a7e42396/python/x402_a2a)

Python packageのversion、HTTP x402のversion、A2A extensionのv0.1、wire上の`x402Version: 1`は別のversion軸である。

## A2A x402が解決すること

A2A x402は、有料のA2A Taskについて次の交換方法を定める。

1. Merchantがどの支払条件を受け付けるかを提示する。
2. Clientが元のTaskへ相関した支払payloadを提出する。
3. Merchantが条件とpayloadを照合し、verify／settleする。
4. 成功または失敗の結果をTaskとreceipt historyに残す。

この仕組みは、利用者がその購入を承認した証拠を定義しない。本プロジェクトではその部分をAP2が担当する。逆にAP2は、A2A Task上の`payment-required`や`payment-submitted`の形式を定義しない。

## 公式v0.1の基本フロー

### 1. 拡張機能の有効化

Agent Cardでcanonical extension URIを宣言し、ClientはTask開始時に同じURIをactivationする。Merchantは完全一致のactivationを確認する。URIの欠落、別version、simulation URIとの混在を暗黙に補正しない。

### 2. PaymentRequired

支払が必要な場合、MerchantはTaskを`input-required`にし、`Task.status.message.metadata`へdotted sibling keyを置く。

```json
{
  "x402.payment.status": "payment-required",
  "x402.payment.required": {
    "x402Version": 1,
    "accepts": [
      {
        "scheme": "exact",
        "network": "...",
        "asset": "...",
        "payTo": "...",
        "maxAmountRequired": "..."
      }
    ]
  }
}
```

requirementsは、元のTask、Merchant、金額、通貨またはasset、network、payTo、有効期間へ結び付ける。

### 3. PaymentSubmitted

Clientは元Taskの`taskId`を持つ新しいA2A Messageでpayloadを提出する。

```json
{
  "x402.payment.status": "payment-submitted",
  "x402.payment.payload": {
    "x402Version": 1,
    "scheme": "exact",
    "network": "...",
    "payload": {}
  }
}
```

Merchantは`taskId`から元のrequirementsを取得し、提出されたscheme、network、asset、payTo、amount、payloadを照合する。facilitatorを使う場合でも、このTask相関とrequirements照合はMerchantの責任である。

### 4. 結果と履歴

各settlement attemptの結果は順序付きの`x402.payment.receipts`へ追加し、最終Taskにも履歴を含める。失敗は`payment-failed`と失敗理由を残し、成功へ読み替えない。利用者が決済承認を拒否した場合は、元Taskへ`payment-rejected`を一回だけ相関し、payloadやsettlementを作らない。

## このプロジェクトのprofile

現在選択できるのはproject-localな`x402-wire-simulation/1`だけである。公式v0.1のデータ形状とTask相関を試験するためのfixtureで、公式A2A x402 profileではない。

| 項目 | 公式A2A x402 v0.1 | 現在のsimulation |
| --- | --- | --- |
| Extension URI | canonical URI | project-local URI |
| scheme | `exact` | `exact-simulated` |
| network | 対応blockchain network | `demo:local` |
| asset | 対応token contractなど | `USD`表記のローカル単位 |
| payload | walletが生成するscheme-defined payload | synthetic proof |
| wallet署名 | 必須の構成要素 | `walletSigned=false` |
| verify／settle | facilitatorまたは対応実装 | ローカルの決定論的検証とSQLite台帳 |
| transaction | on-chain transaction | `sim:`で始まる参照 |
| 適合表現 | 条件を満たせば評価可能 | `NOT CONFORMANT` |

simulationは実資産、wallet署名、facilitator verification、on-chain transactionを表さない。画面、Agent Card、Task、検証結果では公式profileと明確に区別する。

## 現在のTaskライフサイクル

```text
計画承認済み
  → project-local profileをactivationしてMerchant Task開始
  → input-required + payment-required + Checkout
  → 決済承認
  → AP2 Mandate／project-local credentialを生成
  → payment-submitted Message
  → MerchantがTask、Checkout Mandate、payloadを照合
  → fulfillmentをprepare
  → ローカルsimulationをsettle
  → payment-completedまたはpayment-failed
  → 最終Taskに結果履歴と業務Artifactを保存
```

Merchant TaskはMerchant側のpayment subflowの正本である。仲介workflowは最初に返された`taskId`を保持し、別Taskへのpayload差替えや、別profileのmetadataを拒否する。

## AP2との結び付き

A2A x402のrequirementsとpayloadは、AP2の次の値へ相関する。

- Checkout Mandateが参照するMerchant Checkout
- Payment Mandateの金額、通貨、payee、transaction ID
- Credential Providerが検証したaccepted requirements digest
- 決済承認、workflow、plan、Task、settlement attempt
- AP2 Payment Receiptが参照する処理結果

ただし、AP2 Receiptを`x402.payment.receipts`そのものとして扱わない。Task上の結果履歴はAP2 ReceiptのIDやdigestを参照できるが、issuer、schema、意味は別に保つ。

## フェイルクローズの境界

公式profileのadapterは、未設定のままsimulationへfallbackしない。現在は次の要素がないため、canonical URIを使うprofileは起動時に失敗する。

- 対応networkとasset
- Merchantの`payTo`
- walletまたはSigning Service
- scheme-definedな公式`exact` payload
- facilitatorのverify／settle
- TLSと実transaction hashを含む受入証跡

これらを実装して条件付き受入基準を通すまでは、公式profileをenableにしたり、A2A x402 compatible／conformantと表示したりしない。

## エラーと再試行

次の不一致は副作用を開始する前に拒否する。

- extension URIまたはactivationの欠落・混在
- original `taskId`との不一致
- scheme、network、asset、payTo、amount、expiryの不一致
- Checkout、Mandate、credential、payloadのdigest不一致
- 使用済みnonce、capability、idempotency keyの異なるpayloadでの再利用

settlement結果が不明な場合、新しい支払を作らず`reconciliation_required`へ進む。同じexternal IDを照会し、確定証拠が得られるまで`payment-completed`にしない。

## 主張できる範囲

この実装から主張できるのは「A2A x402 v0.1のwire shapeとTask相関を参照したproject-local test fixture」である。公式A2A x402 v0.1のwallet、facilitator、on-chain settlement、相互運用性は実行していない。
